# 自动项目记忆规则

## 目标

让 AI 在完成仓库改动时留下足够项目记忆，方便后续任务接上上下文，同时避免纯问答和小探索制造文档噪音。

## 默认开始动作

每次任务开始先读取：

- `AGENTS.md` 或项目等价 agent 指南。
- README 和相关模块文档。
- 项目状态、任务索引、brief、PRD、design、decision 中与本次任务相关的文件。项目状态通常是 `docs/project-state.md` 或等价滚动事实摘要。
- package、构建、测试或脚本入口。

## 何时不记录

- 纯问答。
- 只读分析。
- 没有仓库改动，且用户未要求沉淀。
- 临时讨论但没有形成结论。

## 何时记录

- 产生代码、配置、脚本、文档、原型或资源改动后，收尾前检查 `git diff --stat` 和 `git status --short`。
- 按任务级别写对应记录：`direct` 写 dev-log，`brief` 写 brief 和 dev-log，`standard` 写 PRD/设计/技术说明和 dev-log，`decision` 写 decision。
- 更新任务索引；每次产生仓库改动后评估项目状态是否需要更新。项目状态只记录会影响后续开发判断的稳定事实。

## 项目状态更新规则

项目状态通常是 `docs/project-state.md` 或项目等价文件。它是滚动事实摘要，不是任务日志。

需要更新：

- 可运行模块、近期重点、已知问题、下一步优先级、长期决策、部署状态、契约边界或核心流程事实变化。
- `standard`、`decision`、跨模块改动或长期流程变化产生会影响后续开发判断的新事实。
- 原本写在项目状态里的限制、风险或下一步已经不再成立。

不需要更新：

- 普通 bugfix、单次实现细节、短期排查过程、临时 TODO。
- 已经写入 dev-log 的任务过程、命令输出、失败尝试或局部实现说明。
- 只影响单次交付、不改变后续 AI 判断方式的改动。

更新时只改稳定事实和必要条目，并同步更新 `最后更新` 或项目等价日期字段。
## 收尾检查

最终回复前确认：

1. 改动范围是否符合用户请求。
2. 新增文件是否都需要。
3. 是否已评估项目状态需要更新；如未更新，原因是否符合规则。
4. 相关验证是否运行并读取结果。
5. 失败或未验证项是否写清原因。
6. 记录位置是否在最终回复中说明。

## 推荐模板

### dev-log 条目

```markdown
## YYYY-MM-DD

### 任务标题

- 改动：说明实际改了什么。
- 验证：列出运行的命令或检查结果。
- 记录：关联 brief、PRD、decision、截图或任务索引。
- 未验证：如有，说明原因和补做命令。
```

### decision 条目

```markdown
# 决策标题

- 日期：YYYY-MM-DD
- 状态：accepted / superseded / rejected
- 背景：为什么要做选择。
- 决策：选择什么。
- 备选：考虑过什么。
- 影响：影响哪些模块和后续任务。
- 复审：什么情况下重新评估。
```
