# 两档开发节奏与取舍指南

## 节奏对照表

| 档位 | 适用场景 | 开工前 | 收尾时 |
| --- | --- | --- | --- |
| 无记录 | 纯问答、只读分析、无仓库改动 | 不需要 | 不改任何文档 |
| **直接改（默认）** | bugfix、文案、样式、小配置、单模块小需求、单接口微调 | 读相关代码与既有测试，直接实现 | 跑对应验证 + 语义化 Git commit。**不写 dev-log、不写看板、不建方案文档。** |
| **先写方案再改（大改）** | 跨端/跨模块契约、数据库表结构变更、权限/状态机重构、多模块新功能、长期架构调整 | 在 `docs/specs/YYYY-MM-DD-<topic>.md` 写 1 份单文件方案（目标、非目标、接口/SQL、边界与验证清单），确认后再写代码 | 跑对应验证；仅当长期稳定事实变化时覆盖更新 `docs/project-state.md`；完成 `docs/TODO.md` 事项直接删行。 |

## 为什么不再使用 4 级分流与多目录文档

在一人开发或小团队高频迭代实践中，`direct / brief / standard / decision` 四级分流叠加 `dev-log`、`iteration-index`、`todo/board`、`prd/`、`design/`、`briefs/`、`plans/`、`decisions/` 极易出现以下退化：

1. **同一改动重复写 5~7 份文档**，文档维护成本超过代码修改本身。
2. **入口索引与状态文件持续膨胀**，每次 AI 启动光读项目记忆就要消耗大量上下文，且混杂过期细节。
3. **中间状态长期空转**（如 `decisions/` 长期为空、看板的 `Ready/Doing/Blocked` 无人维护），徒增心智与校验阻力。
4. **日常流水账与 Git 历史高度重复**，规范的语义化 Git commit 已足够承载日常变更轨迹。

## 瘦身迁移原则

审计已有项目时，遵循「保工程、砍流水账、零丢失归档」：

- **必须保留**：接口契约生成与检查、SQL 增量迁移目录、自动化测试、安全与生产发布 runbook/脚本。
- **归档停更**：把旧的 `dev-log/`、`iteration-index`、`todo/`、历史 `prd/`、`design/`、`plans/` 只读归档至 `docs/archive/`（或原地标注冻结），不再继续追加。
- **活文档封顶**：新入口固定为 `AGENTS.md`、`docs/project-state.md`、`docs/TODO.md` 与按需 `docs/specs/`，并用脚本锁死行数与体积上限。
